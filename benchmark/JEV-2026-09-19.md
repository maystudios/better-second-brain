# Jev retrieval experiment — 2026-09-19

**Decision: reject automatic hard pruning.** Six fixed questions on two private, populated vault snapshots were answered by Gemini 3.8 Flash high. The cheaper shortlist lost answer facts. This experiment does not establish a production cost or quality gain.

## Design

Three questions per vault: direct lookup, a relationship question, and uncertain/missing evidence. The answer oracle, scorer, and hypotheses were frozen before candidate results. Local retrieval supplied complete selected pages, plus the same mandatory roadmap; the Gemini answerer was prohibited from searching beyond those packets. This is a controlled retrieval-and-synthesis comparison, not an unrestricted agent search benchmark. Six fresh Gemini conversations were used: one per vault and arm. Host default sampling settings applied; the CLI has no temperature override.

- A: lexical candidate pool, limit 12.
- B: the same pool, Jev shortlist of 4.
- C: B plus deterministic outgoing links, at most 8 pages.
- B's Jev classifications were reused for C. Reported Jev overhead is charged to each hypothetical arm; actual API calls were shared.

## Interpretation and limitations

Both reduced-context variants failed the quality floor. The lexical baseline also failed full support recall, so it is not a certified high-quality reference. Some facts can be grounded in alternative pages: the frozen scorer measures expected paths, and substring assertions are coarse proxies for semantic correctness. No result is promoted to a general model-quality claim. The production default consequently retains the whole generated candidate pool and exposes ordering/priority; `--prune` is an explicit experimental choice. Missing API credentials or malformed results must preserve the pool.

Candidate-generation recall remains bounded: Jev cannot rank a page that the local search never supplied. Expand the query, follow links and read full pages before answering; no rank proves global absence. The default retained-pool policy is a conservative response to this negative experiment, not a separately demonstrated efficiency win.

Protocol deviation discovered on readback: the draft retriever capped **snippet windows**, not distinct documents as the frozen hypothesis description intended. Repeated windows from the same page reduced document diversity. These results therefore describe that draft's window-ranking implementation; they cannot validate a 12-document BM25 baseline. The mismatch and poor support recall are additional reasons to reject the pruning policy rather than tune the oracle or advertise savings. The two snapshots contained 130 and 564 wiki Markdown pages.

## Round 2: corrected document retriever

The candidate generator was corrected to BM25-style rare-term weighting with
title/alias bonuses and **one candidate per document**. The same frozen oracle,
questions, complete-page packet format, Gemini model, and A/B/C policies were
reused in six new conversations. B explicitly used experimental `--prune`.
This was a protocol correction, not a change to the answer key or scoring floor.

The six shared classification calls cost approximately $0.00108 at the same
input list price. **Less source text did not translate into fewer host tokens**:
B used about 9.7% more reported input/output tokens than A. Agent reading/tool
behavior and repeated context handling affect the total; context bytes alone
are not an efficiency result. One trial per vault/arm is too small to estimate
a stable latency or cost effect.

Readback confirmed a genuine lost technical support page in B/C: the resulting
answer could explain a replication symptom but correctly abstained from giving
the requested configuration fix because its packet lacked the evidence. The
unchanged scorer also produced a false negative for A on an English paraphrase
that conveyed the required event using a hyphenated expression absent from the
substring list. That limitation is recorded here; scores and oracle remain
unchanged. The formal floor remains false for all three arms. The scorer's
floor does not itself include citation coverage, so citation coverage is
reported separately and cannot be silently treated as passed.

Decision remains **DISCARD automatic hard pruning**. Preserve all lexical
candidates by default. Neither round demonstrates a production quality or cost
gain from Jev; the second round does show improved candidate recall from the
deterministic retriever correction. Native hook/transaction safety is evaluated
separately from the retrieval-quality claim.

## Maintenance and integration checks

Four isolated synthetic scenarios embedded in copies of existing vault pages
exercised insertion, link creation, unlinking, deletion, index/log updates and
rollback through real Jev review calls. All four applied and restored original
bytes; raw sources stayed unchanged. Both attempted deletions with live
backlinks were blocked before review. These are transaction tests, not proof
that Jev can autonomously maintain factual quality in arbitrary vaults.

52 automated tests cover offline/default behavior, malformed responses, native
host contracts, UTF-8 and Windows paths, signed/stale plans, backlinks, failed
write restoration, upgrade preservation and rollback. An independent Gemini
code review accepted the bounded integration after earlier defects were fixed.
A real Antigravity/Gemini edit was denied by the installed native hook. Codex
and Claude payloads/installers were contract-tested; no equivalent live model
session is claimed for those hosts.

## Reproduction and privacy

Private prompts, source text, golden excerpts, hash manifests, model event logs and answers stay in the local ignored evaluation workspace. No private vault content is included here. Repeat with your own corpus by freezing an oracle first, using the same questions/model across arms, saving complete retrieved pages and raw model usage, and independently checking fact/citation coverage. Do not tune the scorer to rescue a candidate.
